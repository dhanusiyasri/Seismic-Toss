## Evidence basis
The design keeps tilt/deformation as an important monitoring signal and treats multi-sensor/spatial evidence as complementary rather than claiming any one low-cost sensor is a definitive subsidence measurement. Current geotechnical monitoring literature supports continuous inclinometric/deformation monitoring as a useful part of stability monitoring, while modern mine-subsidence systems often combine multiple sensing modalities such as GNSS/InSAR/fibre-optic measurements.

## Explicit limitation
The project is a prototype. The simulator labels are generated by software rules, not confirmed mine events. Therefore automated accuracy against those labels demonstrates internal scenario consistency, not real-world safety performance. Real deployment requires site-specific sensor calibration, ground-truth events, geotechnical thresholds, redundancy, uncertainty analysis and safety review.


## AI / alert / offline architecture hardening (September 2026)

The active decision path is now deliberately separated into four layers:

```text
Raw gateway packet
   ↓
Time-aware features + rolling stability
   ↓
Temperature-scaled multiclass ML
   ↓
Independent engineering screen
   ↓
ONE authoritative risk fusion
   ↓
Alert state machine
   ↓
Dashboard / GIS / notification log
```

### AI model: what the score means

- **Anomaly score** = `100 × (1 − P(NORMAL))`. It answers: “How far is this reading from the learned normal class?”
- **ML risk score** = a class-severity score derived from calibrated NORMAL/WARNING/CRITICAL probabilities.
- **Physical screen** = an independent deterministic check using tilt, tilt rate, acceleration deviation, vibration, FSR/deformation, and cross-node differences.
- **Final risk score** = `0.70 × ML risk + 0.30 × physical screen`.
- Large instantaneous tilt/acceleration excursions can still force CRITICAL so model uncertainty cannot hide an obvious physical excursion.
- The classifier is **temperature-scaled**, so the displayed class probabilities are explicitly calibrated on a held-out calibration split rather than being presented as raw logistic probabilities.

The runtime model is a JSON artifact, so inference does not load a scikit-learn pickle. This keeps the active inference path portable and suitable for an offline/local deployment.

The current training run uses 18,211 rows (existing simulator/edge-risk records plus physics-informed synthetic states). The held-out test accuracy is 0.9929 and balanced accuracy is 0.9938; test log loss is 0.0189 after temperature scaling. These are **software-label consistency metrics**, not field accuracy. They must not be presented as evidence that the system can certify a real mine.

### Why this architecture is preferable to the old score mapping

The previous system could use an Isolation Forest decision score as if it were a probability and then feed that score into another weighted risk calculation. That mixed two different meanings of “anomaly” and “risk”. The new path keeps the semantics separate:

1. the classifier estimates class probabilities;
2. the anomaly score measures departure from normal;
3. the physical screen supplies deterministic engineering evidence;
4. the risk engine performs the only final fusion;
5. alerts consume only that final state.

This avoids double-counting the same signal in multiple layers.

### Alerts and notifications

Alerts are now a state machine, not a timer:

- NORMAL → WARNING/CRITICAL: create one alert.
- WARNING → WARNING: no new alert.
- WARNING → CRITICAL: create one escalation event and close the previous state.
- CRITICAL/WARNING → NORMAL: close the active incident and create one recovery record.
- Node 2 OFFLINE/ONLINE follows the same transition principle.
- Acknowledgement records operator awareness; recovery is automatic from sensor state.
- The default notification channel is **LOCAL/DASHBOARD only**. The prototype never pretends that an email or SMS was sent.
- External channels remain explicit integrations rather than simulated success records.

### Offline mode

The frontend now has two offline layers:

1. **Service worker:** keeps the application shell available after the first successful load.
2. **Local API snapshot cache:** successful GET responses are retained locally. If the backend/network disappears, the UI can continue showing the last known sensors, AI state, history and alerts.

The UI explicitly changes to **“Offline mode — showing last known data”**. It does not imply that the sensor network is still live. Write actions such as acknowledgement are not faked while disconnected.

Offline mode is therefore a last-known-state monitoring mode, not an invented live-data mode. Real gateway store-and-forward can be added at the hardware/network layer later; the browser itself cannot recover measurements that never reached it.

- Removed legacy Isolation Forest runtime artifacts from the distribution.
